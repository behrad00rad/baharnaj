# Flexible service pricing

Service catalog uses `pricing_type` (FIXED, STARTING_FROM, RANGE, CONSULTATION, VARIABLE), the existing `price` for fixed prices, optional `minimum_price` / `maximum_price`, and `pricing_note`. Variable pricing requires an explanatory note; its minimum is optional. Irrelevant inputs are ignored/normalized. Existing services default to FIXED without changing prices or slugs.

Every new appointment item freezes its catalog terms in `catalog_pricing_snapshot` in all three creation paths (guest, admin, employee). `price_snapshot` remains untouched after creation. A nullable `final_price` holds the agreed amount for non-fixed items. Historical items with an empty catalog snapshot always remain fixed, even if the current service catalog changes. `effective_price` is the single financial accessor: historical/fixed snapshot or the agreed final price; unresolved estimates contribute nothing. API totals are agreed subtotals accompanied by `has_unresolved_prices`.

Admins and the employee assigned to an item finalize it through the existing appointment detail panels. The backend action locks the appointment/item, validates nonnegative whole toman amounts, checks ownership and logs old/new amounts. Fixed snapshots cannot be changed through this action. Cancelled/completed items and appointments with pending/confirmed/refunded payments cannot be repriced. Generic booking/item serializers cannot accept client-supplied snapshots or final prices. The Django maintenance admin exposes these item fields read-only.

Payment recording, employee reports and confirmation require all appointment prices to be final. Partial payments remain supported after finalization; this does not introduce an estimate-based deposit system. Variable-service completion requires its agreed price, and its commission is created from that price after confirmed full settlement (or on completion if already settled). Existing fixed-service commission behavior remains unchanged. Finance allocations and service revenue use `effective_price`; cash revenue remains based on confirmed payment/refund records.

One frontend formatter handles every service mode. Public cards, service details, related links, booking selections and employee selection show appropriate prices. Mixed bookings show the fixed subtotal plus the unresolved-pricing explanation. Admin service forms show only relevant fields. Appointment panels display catalog and agreed prices separately, with clear unresolved/estimated/final states. Existing SEO schema contains no numeric Offer price; no guessed prices were introduced.

Migration 0025 is additive apart from giving the existing Service.price a default for non-fixed service creation. It preserves SQLite overlap triggers on upgrade and rollback.
