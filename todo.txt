## Must-fix product problems

### 1. Make employee/admin login discoverable

The staff login exists at `/login`, but every public “ورود” button currently links directly to customer login in [PublicLayout.jsx](/workspaces/baharnaj/frontend/src/components/PublicLayout.jsx:69).

Recommended design:

- “ورود” opens a small account-choice screen:
  - حساب مشتری
  - ورود کارکنان
- Add `/staff/login` as the clear staff URL.
- Add a discreet “ورود کارکنان” link in the footer.
- Show the appropriate panel link when already authenticated.
- Put employee logout in the header or navigation, not only inside Profile.

This directly explains the second item in [todo.txt](/workspaces/baharnaj/todo.txt:2).

### 2. Redesign the customer dashboard

The customer dashboard works, but it currently looks like a thin administrative panel. Most of [CustomerApp.jsx](/workspaces/baharnaj/frontend/src/pages/CustomerApp.jsx:48) is compressed into basic cards with little hierarchy.

The improved dashboard should have:

- A prominent “next appointment” hero card.
- Persian date, remaining time, specialist photo, services, duration and clear status.
- One primary action per state: manage, contact salon, or book again.
- A mobile bottom navigation rather than a horizontally scrolling menu.
- Proper colored status chips for pending, confirmed, completed and cancelled.
- A timeline in appointment details.
- Better loading skeletons and retry buttons.
- A notification badge in the navigation.
- Separate “Personal information,” “Password and security,” “Preferences,” and “Delete account” sections.
- The deletion controls inside a collapsed danger zone.
- Confirmation dialogs instead of browser `window.confirm`.
- Consistent rounded surfaces, spacing and typography matching the public website.
- A proper receipt layout suitable for printing or saving.

This should be treated as a redesign, not a few CSS tweaks.

### 3. Complete cancellation and rescheduling rules

Customer cancellation and rescheduling are still controlled by one global on/off flag in [views.py](/workspaces/baharnaj/backend/salon/views.py:762). There are no actual deadlines, fees, service exceptions or salon-configurable rules.

Required:

- Configurable cancellation deadline.
- Configurable rescheduling deadline.
- Optional cancellation/no-show fee.
- Different rules by service if needed.
- Server-side enforcement based on Tehran time.
- Clear explanation before confirmation.
- Show the exact deadline on each appointment.
- Record the customer’s reason.
- Audit every mutation.
- Make the same policy apply to guest booking management.

Until this exists, customer self-service is intentionally disabled.

### 4. Repair customer identity integrity

`User.phone` is not unique, partly because historical guest bookings can create multiple records. This creates long-term ambiguity.

Required:

- Normalize all existing Iranian phone numbers.
- Distinguish login accounts from guest-only records.
- Guarantee one active login-capable customer per normalized phone.
- Build a verified historical-booking claim/merge process.
- Never attach historical bookings based only on a typed phone number.
- Provide an admin conflict-resolution screen.
- Test duplicate phone, email and legacy record cases.

This is the most important backend task before treating customer accounts as mature.

### 5. Store legal acceptance properly

Signup currently validates `accept_terms`, but then discards it. The system needs to store:

- Terms version.
- Privacy-policy version.
- Acceptance timestamp.
- Source: standalone signup or booking.
- IP/user-agent if legally appropriate.
- History when policies are updated.

Marketing consent already has some audit fields, but account terms acceptance does not.

### 6. Build the account-deletion admin workflow

The customer can submit a request and the model supports statuses, but there is no admin workflow to process it. See [models.py](/workspaces/baharnaj/backend/salon/models.py:143).

Add:

- Admin deletion-request queue.
- Pending/approved/rejected/completed states.
- Processing notes and confirmation.
- Defined anonymization rules.
- Protection of required financial records.
- Customer-visible request status.
- Ability for the customer to cancel a still-pending request.
- Audit log for every decision.

### 7. Fix the admin customer list

The “مدیریت مشتریان” screen calls `admin/users/`, whose backend queryset contains every user, including employees and admins:

- Frontend: [AdminApp.jsx](/workspaces/baharnaj/frontend/src/pages/AdminApp.jsx:2213)
- Backend: [views.py](/workspaces/baharnaj/backend/salon/views.py:886)

It needs a customer-specific endpoint and interface showing:

- Customer name and phone.
- Account versus guest status.
- Upcoming and previous visits.
- Total confirmed spending.
- No-show count.
- Preferences and internal notes.
- Identity conflicts.
- Deletion requests.
- Search, filters and pagination.

### 8. Correct employee leave behavior

The documentation says employee leave requires admin approval, but the implementation makes an employee-created `TimeOff` entry effective immediately. There is no approval status in the model, and the endpoint saves it directly in [views.py](/workspaces/baharnaj/backend/salon/views.py:1713).

Choose and implement one truthful workflow:

- Recommended: request → pending → admin approves/rejects → schedule is blocked.
- Or explicitly allow employees to manage leave directly and update all wording.

The approval workflow is safer for salon operations.

## Customer-flow correctness issues

These are smaller than the identity and policy work, but still necessary:

- `recent_history_count` can never exceed three because the backend counts a sliced three-item queryset.
- Appointments and notifications return paginated results, but the customer UI has no next/previous or infinite-loading controls.
- Partial payment and partial refund states are incorrectly displayed as “در انتظار پرداخت”.
- Payment methods and some statuses appear as raw backend values.
- Notification `target_url` is returned but not used; clicking a notification should open the relevant appointment.
- “Book again” returns preferred specialists, but the booking wizard ignores them.
- Rescheduling uses a native Gregorian date field while the rest of the system uses Persian/Jalali selection.
- Rescheduling shows “no times found” while availability may still be loading.
- Booking employee selection shows “no specialist” before requests have necessarily completed.
- The five-minute booking hold has no visible countdown or expiry recovery.
- Expired holds should offer one-click rechecking instead of a generic failure.
- The review screen needs edit links for service, specialist, time and contact details.
- Booking confirmation should show specialists, formatted Persian date, price state and total duration.
- Add copy/share/print actions for confirmation codes.
- A refreshed guest confirmation page currently loses the original confirmation view.
- The guest management title mentions changing a booking, but the screen only supports lookup, contact and conditional cancellation.

## Authentication UX

- Password requirements visible before submission.
- Password-strength and matching feedback.
- Loading and duplicate-submit protection on password recovery.
- Error handling on failed password-recovery requests.
- Expired/used reset-link screen with a clear restart action.
- Redirect an already logged-in user away from irrelevant login/signup pages.
- Show customers where to find staff login, and staff where to find customer login.
- Write actual `AccountLogin` records; the model exists but is never used outside Django admin.

Email delivery configuration is operational, but the application should still have a branded HTML reset template and tests using Django’s in-memory email backend.
